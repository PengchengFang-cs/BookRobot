# FPC 项目记录体系设计

## 目标

在 `docs/` 下建立一套供人和后续 Agent 共同使用的项目记录体系，同时满足两个需求：

- 用短小、持续更新的当前视图说明项目主线、进度、未解决问题和下一步工作。
- 永久保存已经发生的故障、重要操作、判断和验证结果，方便以后追溯，不能因为问题已经解决就删除历史。

这套文档只记录可公开提交的工程信息，不保存密码、密钥、证书、数据集、模型、日志文件或缓存。

## 方案

采用“统一索引 + 当前视图 + 分类历史”的结构。当前视图帮助 Agent 快速进入工作状态；历史文档提供证据和决策背景；已有功能设计与实施计划继续保留在 `docs/superpowers/` 中，由统一索引链接。

没有采用单一大日志，因为当前状态会很快淹没在历史中。暂时也不为每个故障创建单独文件，因为现阶段问题数量有限，集中编号更便于维护；当故障档案明显过长时，可以按年份归档，但编号和内容仍然保留。

## 文档结构

### `docs/README.md`

项目文档入口，规定后续 Agent 的阅读顺序，并链接下面所有文档以及已有设计和实施计划。

推荐阅读顺序：

1. 仓库根目录 `AGENTS.md`，了解写入范围和真机动作约束。
2. `docs/PROJECT_MAINLINE.md`，了解项目目标和系统边界。
3. `docs/CURRENT_STATUS.md`，了解当前进度、问题和下一步。
4. 根据任务查阅 `docs/ROBOT_ISSUES.md`、`docs/WORKLOG.md`、`docs/ROADMAP.md` 或具体设计/计划。

### `docs/PROJECT_MAINLINE.md`

记录长期稳定的项目事实：

- 当前工程基于可废弃的 FruitTest demo 改造，不直接修改机器人上的其他旧工程。
- RTX 5090 与 Wanda 的职责分工，以及当前书本感知数据链。
- 本地与机器人工作副本的位置。
- GitHub 只作为公开备份，部署不依赖机器人从 GitHub 拉取；正常部署方向是从 5090 通过 SSH 更新 Wanda 的 `/home/unix_ai/fpc`。
- 机器人其他目录只允许读取和复制，修改只发生在两个 `fpc` 工作路径中。
- 硬件动作必须由用户明确授权并确认现场环境。

长期规则发生变化时直接更新本文件，同时在工作日志中留下变更记录。

### `docs/CURRENT_STATUS.md`

这是最常更新的当前视图，只保留仍然有效的内容：

- 当前阶段与目标。
- 已完成并仍适用的能力。
- 正在进行的工作。
- 当前未解决或需复测的问题。
- 下一步建议顺序。
- 最近更新时间。

历史问题解决后从“当前问题”移除，但原条目继续保存在故障档案中。

### `docs/ROADMAP.md`

记录阶段性计划及其状态，不代替详细实施计划。初始阶段包括：

1. 书本二维检测与 Wanda 本地三维吸取点验证。
2. 底盘转向和接近控制验证。
3. 吸书动作与固定距离调整。
4. 感知、导航、机械臂的完整任务串联。
5. 比赛现场联调和重复性测试。

具体功能的设计与任务分解仍写入 `docs/superpowers/specs/` 和 `docs/superpowers/plans/`。

### `docs/ROBOT_ISSUES.md`

这是永久故障档案。每个问题使用稳定编号 `BOT-YYYYMMDD-NN`，至少包含：

- 标题和状态：`待处理`、`调查中`、`已绕过`、`已解决` 或 `无法复现`。
- 首次发现时间和最近更新时间。
- 现象及影响。
- 复现条件。
- 已确认事实与测量证据。
- 根因；如果没有确认，必须标记为“假设”，不能写成事实。
- 已采取的处理或临时绕过方法。
- 验证结果和剩余工作。
- 相关代码、配置或工作日志链接。

条目只追加和更新状态，不删除。初始档案将记录：重启后底盘未释放、遥控平移正常但旋转指令为零、30° `/spin` 测试最终总角度约 57.8°。最后一个问题会明确区分 `/spin` 反馈约 32.9°和总里程计角度约 57.8°，并将首次释放流程列为待复现假设，而不是已确认根因。

### `docs/WORKLOG.md`

按日期倒序记录重要工程活动。每条记录包含目的、做了什么、结果、相关问题编号和后续动作。它记录的是过程，不代替当前状态或故障结论。

初始记录会覆盖：

- SSH 免密与反向隧道形成的 5090 到 Wanda 工作通道。
- FruitTest 工作副本和 GitHub 公开备份的定位。
- 书本感知替换、审查与修复的当前结果。
- 真机底盘释放、前后移动、遥控旋转和 `/spin` 测试。
- 使用低速 `/odom` 闭环把机器人从约 57.8°修正到约 30.2°。

## 一致性与维护规则

- `CURRENT_STATUS.md` 中每个当前机器人问题必须链接到 `ROBOT_ISSUES.md` 的稳定编号。
- 已解决的问题从当前问题列表移除，但故障档案和工作日志保持不变。
- 同一事实只选择一个权威位置；其他文档通过链接引用，避免复制后产生冲突。
- 数值、状态和根因判断必须来自实际命令输出或用户现场观察。未经验证的判断标为假设。
- 每次完成重要实现、真机实验、部署或问题调查后，更新当前状态和工作日志；涉及机器人异常时同时更新故障档案。
- 文档中的时间使用 `YYYY-MM-DD`，必要时注明时区；机器人现场记录默认使用 Asia/Shanghai。
- 不在 Git 中写入密码、私钥、令牌或证书内容。现有连接只记录主机别名、用户和非敏感路径。

## 验证方式

文档落地后执行以下检查：

- 所有索引链接指向仓库内存在的文件。
- `CURRENT_STATUS.md` 的当前问题均能在故障档案找到对应编号。
- 故障条目明确区分事实、用户观察和待验证假设。
- 主线说明与根目录 `AGENTS.md`、`README.md` 不矛盾。
- 使用 `rg` 检查没有密码、私钥块、令牌或证书内容进入新增文档。
- 执行 `git diff --check`，确保 Markdown 没有空白错误。
