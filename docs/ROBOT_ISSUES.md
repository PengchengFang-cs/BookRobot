# 机器人故障档案

本文件保存带稳定编号的机器人问题历史。历史条目永不删除；问题变化时更新状态、最近更新时间、验证结果和剩余工作，不复用编号，也不把绕过方案写成永久修复。

## 状态定义

- **待处理**：问题已记录，但尚未开始系统调查。
- **调查中**：正在收集证据或隔离故障边界，根因尚未确认。
- **已绕过**：已有可恢复功能或继续受控测试的临时方法，但永久修复尚未确认。
- **已解决**：已实施永久修复，并按记录的验证方法确认问题消失。
- **无法复现**：在明确记录的环境和步骤下未能再次观察到问题；这不等于已解决。

所有原因判断都必须区分确认事实与推测。没有直接证据支持的原因必须明确标为**假设**，不得写成已确认根因。

## BOT-20260818-01

- **标题**：重启后底盘不响应
- **首次发现**：2026-08-18（Asia/Shanghai）
- **最近更新**：2026-08-18（Asia/Shanghai）
- **状态**：已绕过
- **现象与影响**：机器人重启后，网络、ROS 和 controller 健康，但底盘不响应移动控制；当时无法用底盘继续真机测试。
- **复现/上下文**：发生在机器人重启后的释放流程中。项目路径 `/home/unix_ai/fpc/release_base.sh` 通过 `fruit_movebase_mode_controller` 的 `movebase_mode_command/mode_command` 依次发送 `5` 和 `0`。
- **确认事实与证据**：
  - 重启后网络可达，ROS 与 controller 状态健康，但底盘不响应。
  - `movebase_mode.yaml` 存在。
  - 用户在机身执行释放/旋转释放，并重启机器人页面后，已现场确认前进和后退恢复可用。
- **根因或假设**：确切硬件 mode 语义没有可用文档，当前证据不足以确认更深层根因。不得把 `5`、`0` 或机身操作分别解释为某个确定硬件状态。可能存在重启后 mode transition 或释放状态未完成的情况，但这仅是**假设**。
- **处理**：执行现有 `release_base.sh` 流程；用户随后在机身执行释放/旋转释放并重启机器人页面，以恢复底盘移动。该处理是现场绕过方案，不是永久修复。
- **验证**：用户现场操作后确认机器人可前进、后退；网络、ROS 和 controller 保持健康。
- **剩余工作/链接**：查找或补充硬件 mode 的权威语义文档；设计可重复的重启后状态检查，区分脚本 mode transition、机身释放和机器人页面重启各自的作用。相关当前状态见 [`CURRENT_STATUS.md`](CURRENT_STATUS.md)。

- **验证**：用户现场确认旋转恢复可用，并完成机器人位置调整。
- **剩余工作/链接**：无需为本条修改代码；如果以后再次出现“正确操作但不旋转”，应创建新问题或以新证据重新打开本条。历史过程见 [`WORKLOG.md`](WORKLOG.md)。

## BOT-20260818-03

- **标题**：组合释放与 `30°` spin 后总航向约 `57.8°`
- **首次发现**：2026-08-18（Asia/Shanghai）
- **最近更新**：2026-08-18（Asia/Shanghai）
- **状态**：已绕过
- **现象与影响**：用户授权在空旷环境中左转 `30°`；连续执行 release 与 spin 的整个组合序列后，最终 odom 总航向约为 `57.8°`，而 `/spin` 自身末反馈约为 `32.9°`。由于缺少 release 后、spin 开始前的独立 odom 基线，约 `24.9°` 仅是尚未被 spin 反馈解释的残差观察，不能据此认定 `/spin` 本身不一致或把残差归入某个执行阶段；当前仍不能把 `/spin` 当作精确旋转原语。
- **复现/上下文**：首次重启后连续执行底盘 release 与 spin。向 `/spin` 发送目标 `0.5235987756 rad`（`30°`），随后读取 `/spin` 反馈、`/odom` 和 `odom -> base_link`。
- **确认事实与证据**：
  - 在组合执行 release 与 spin 之前读取的 odom 航向约为 `0°`。
  - 没有在 release 完成后、spin 开始前读取独立 odom 基线，因此无法从现有记录分别计算两个阶段的航向变化。
  - `/spin` 调用成功，末次反馈约 `0.5735 rad`（`32.9°`）。
  - 最终 `/odom` 和 `odom -> base_link` 航向均约 `1.009 rad`（`57.8°`），与用户现场观察的约 `60°` 一致。
  - 按组合序列前约 `0°` 的读数，约 `57.8°` 是 release 与 spin 整个组合序列的总航向变化；它与 `/spin` 末反馈约 `32.9°` 相减得到约 `24.9°` 的未解释残差。这是读数之间的观察，不能证明 `/spin` 本身不一致，也不能证明残差发生在 release、mode transition、spin 或其他阶段。
  - 在一次性低速、基于 `/odom` 的闭环右转修正中，航向从 `57.799°` 修正到 `30.307°`，后续静态读数约 `30.2°`。
  - 修正完成后 twist 各分量均为 `0`，`diffbot_base_controller` 为 active。
- **根因或假设**：永久根因未确认，现有证据不能定位约 `24.9°` 残差来自哪个阶段，也不能确认 `/spin` 本身存在偏差。首次重启后 release 与 spin 连续执行，release/mode transition 可能对该残差有贡献，但这仅是待复现的**假设**。需要在 fresh reboot 后单独测量 release 前后以及 spin 前后的 odom 才能判断。
- **处理**：经用户授权，在空旷处进行一次性低速 `/odom` 闭环右转，将航向修正回约 `30°`。在问题隔离前，不使用 `/spin` 作为精确原语；受控旋转测试使用 odom feedback。该方法是测试绕过方案，不是永久修复。
- **验证**：闭环修正后 odom 为 `30.307°`，随后静态约 `30.2°`；twist 全为 `0`，`diffbot_base_controller` 保持 active。
- **剩余工作/链接**：在 fresh reboot 的安全受控实验中，分别记录 release 前、release 后、spin 前、spin 反馈过程和 spin 后的 odom，首先验证 release/mode transition 是否引入航向变化；在完成隔离和重复性验证前，继续采用 odom feedback。当前状态见 [`CURRENT_STATUS.md`](CURRENT_STATUS.md#当前问题)。

## BOT-20260818-04

- **标题**：perception-only 入口未加载已有 gRPC 运行环境
- **首次发现**：2026-08-18（Asia/Shanghai）
- **最近更新**：2026-08-18（Asia/Shanghai）
- **状态**：已解决
- **现象与影响**：直接运行 `test_book_perception.py` 时在创建 `BookVisionClient` 阶段报 `BookVisionError: grpc_not_installed`，尚未进入相机或 5090 推理。
- **复现/上下文**：机器人系统 Python 的默认 `sys.path` 不包含视觉运行包自带的 gRPC sysroot；项目配置中的默认证书和 protobuf 路径也不是当前机器人实际安装位置，三个视觉身份变量默认为空。
- **确认事实与证据**：
  - gRPC 已安装在 `/home/unix_ai/.local/share/bookbot/vision-rpc/runtime/sysroot/usr/lib/python3/dist-packages`，现有视觉 runner 会把该目录加入 `PYTHONPATH`。
  - 当前证书、客户端私钥和 protobuf 位于机器人已有的 vision-rpc 运行目录，不在项目配置的默认路径。
  - 临时加载 sysroot 并传入当前 listener 身份与实际文件路径后，`BookVisionClient` 可以连接 `127.0.0.1:7443`。
- **根因或假设**：确认根因是新的 perception-only 入口没有复用机器人既有视觉 runner 的 Python 和运行身份环境。
- **处理**：新增并部署 `scripts/book_vision_env.sh`，由 `run.sh --book-align` 加载现有 gRPC sysroot、protobuf、证书路径和当前视觉服务身份；没有把凭证内容写入 Git。
- **验证**：正式 `--book-align` 入口成功连接 7443 服务并在真实画面返回 5 本书，随后完成底盘对位与移动后复检。
- **剩余工作/链接**：当前无需继续处理；视觉服务身份或安装位置变化时同步更新环境脚本。当前状态见 [`CURRENT_STATUS.md`](CURRENT_STATUS.md)。

## BOT-20260818-05

- **标题**：关节历史缓存不足导致同步 RGB-D 快照无法形成
- **首次发现**：2026-08-18（Asia/Shanghai）
- **最近更新**：2026-08-18（Asia/Shanghai）
- **状态**：已解决
- **现象与影响**：运行环境修正后，默认 pipeline 返回 `ok=false`；诊断入口在 5 秒内仍无法形成同步 RGB-D、CameraInfo 与关节快照，因此没有调用 5090。
- **复现/上下文**：五条输入 topic 均有发布者。同步器允许 RGB-D 和关节时间戳相对彩色帧各偏差 `100 ms`，但关节历史默认仅保留 64 条。
- **确认事实与证据**：
  - 同一窗口中，彩色帧到最近深度帧约 `72.9 ms`，CameraInfo 为 `0 ms`，均在 RGB-D 阈值内。
  - 彩色帧到缓存中最近的 `body_joint`、`joint_head0`、`joint_head1` 分别约 `828.3 ms`、`830.4 ms`、`830.4 ms`；图像对应时刻的关节样本已经被高频关节消息挤出 64 条缓存。
  - 只在单次进程中把 `joint_buffer_size` 从 64 扩大到 512 后，同一 pipeline 成功返回 `base_link=(1.082, 0.292, 0.740) m`。
  - 本次叠加图显示 5090 mask 覆盖画面下缘的绿色长方形目标，但目标部分贴近或超出画面下边缘。
  - 随后把头部从约 `0 rad` 平滑移动到现有标定低头姿态 `joint_head1=0.24997 rad`；新画面可见桌上 5 本书，pipeline 正确覆盖最左侧绿色书并返回 `base_link=(0.630, 0.262, 0.777) m`。
  - 将 FruitTest 从单书返回改为置信度阈值 `0.25`、最多 5 本后再次拍摄；5090 返回的 5 个候选均通过 Wanda 本地几何，置信度范围 `0.538–0.565`，同一张叠加图分别覆盖全部五本书。
- **根因或假设**：确认根因是默认关节历史保留时间短于实测图像消息到达延迟，不是相机 topic 缺失或 5090 无响应。
- **处理**：同步器永久使用 512 条关节历史，并将关节最大时间偏差调整为实测可用的 `250 ms`；对应回归测试已加入项目。
- **验证**：部署后真实 `--book-align` 在移动前后均形成同步快照，分别返回 5 本书，并成功完成对位闭环。
- **剩余工作/链接**：长短轴、机器人视角近端、右边缘和固定偏移诊断仍属于感知几何验收工作，但不再属于本缓存故障。当前状态见 [`CURRENT_STATUS.md`](CURRENT_STATUS.md)。

## BOT-20260818-06

- **标题**：头部 1080p 彩色图在 BEST_EFFORT 订阅下整帧丢失
- **首次发现**：2026-08-18（Asia/Shanghai）
- **最近更新**：2026-08-18（Asia/Shanghai）
- **状态**：已解决
- **现象与影响**：`--book-align` 超时并返回 0 本；超时诊断显示 `color=0, depth=8, info=8`，因此没有调用 5090。
- **复现/上下文**：相机发布 1920×1080 彩色原始图。项目最初对彩色、深度和 CameraInfo 统一使用 ROS sensor-data 的 `BEST_EFFORT` QoS。
- **确认事实与证据**：
  - 故障时 `/head_rgbd/color/image_raw` 有一个 publisher，独立 `ros2 topic hz` 实测约 `5 Hz`。
  - 同一进程在 20 秒内收到 8 条深度、8 条 CameraInfo，但没有收到完整彩色消息。
  - 将 RGB-D 与 CameraInfo 订阅改为 `RELIABLE` 后，正式入口收到彩色帧；首个 RPC 失败后还能取得下一组新鲜帧并识别 5 本书。
- **根因或假设**：确认故障边界是大尺寸彩色消息在 `BEST_EFFORT` 订阅下没有完整送达当前进程。底层是否由 DDS 分片丢包、队列或其他传输细节造成未单独证明，不作更深归因。
- **处理**：RGB-D 与 CameraInfo 改用深度 2 的 `RELIABLE` QoS；关节订阅保持 sensor-data QoS。
- **验证**：部署后完整 `--book-align` 成功完成移动前检测、真实底盘对位、移动后检测并正常退出。
- **剩余工作/链接**：当前无需继续处理；若彩色帧再次消失，应先记录 publisher 频率和本进程缓存计数再重新打开本条。

## BOT-20260818-07

- **标题**：旧导航升降上限 `0.300 m` 与当前真机可达位置不一致
- **首次发现**：2026-08-18（Asia/Shanghai）
- **最近更新**：2026-08-18（Asia/Shanghai）
- **状态**：已绕过
- **现象与影响**：首次对位在横向移动后进入升降步骤，要求从当前 `0.280 m` 上升到约 `0.288 m`；15 秒内位置保持 `0.280 m`，旧适配器以 `torso target was not reached` 退出，前后对位未执行。
- **复现/上下文**：`navnav_final` 的 `build_base_alignment_commands` 接受 `[0.0, 0.3] m`，按 `current + observed_z - reference_z` 生成绝对升降目标。
- **确认事实与证据**：
  - 故障时 `/lifting_controller/joint_states` 报告 `body_joint=0.280 m`、速度为零。
  - 所需高度增量约 8 mm，旧导航生成约 `0.288 m` 目标，但真机在超时前没有越过 `0.280 m`。
  - FPC 对位入口把升降目标裁到 `0.280 m` 后跳过不可执行的高度命令，横向和前后对位成功完成。
  - 移动后高度残差仍约 `+0.009 m`，与未执行上升一致。
- **根因或假设**：已确认旧导航允许的上界与本次真机可达反馈不一致；`0.280 m` 是否为硬件、控制器配置或当时状态的永久上限尚无权威文档，因此更深原因仍未确认。
- **处理**：当前 FPC 书本对位将目标裁到 `0.280 m` 并继续 X/Y 导航，同时保留最终 Z 残差。没有修改只读参考工程 `navnav_final`。
- **验证**：处理后完整对位成功退出，最终平面残差为 `dx=-0.011 m, dy=-0.026 m`，高度残差为 `dz=+0.009 m`。
- **剩余工作/链接**：在接入固定 DataReplay 抓取动作前，确认升降柱权威行程和抓取姿态对约 9 mm 高度残差的处理方式。当前状态见 [`CURRENT_STATUS.md`](CURRENT_STATUS.md#当前问题)。
